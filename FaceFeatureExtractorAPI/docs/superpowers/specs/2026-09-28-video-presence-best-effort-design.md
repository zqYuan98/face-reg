# TASK-2026-001 现场低质量视频关键帧比对修订设计

日期：2026-09-28。状态：口头方案已确认，独立规格审查已通过，待用户审阅本文；不是已实现或已部署说明。

## 1. 已确认需求与本次范围

输入一张参考人脸照片和一段视频，实际比较照片与视频人脸关键帧，判断本次扫描是否检测到匹配。现场视频可能模糊、偏暗、侧脸、小脸或多人；只要仍能形成有效特征就应尝试比较。不要将活体检测、合同持续一致性规则或较高的拍照质量标准作为前置条件。

用户已确认选择“有预算的抽帧与邻近帧补采、质量软提示、三类结果”。备选的全帧人脸检测比对能提高时间覆盖，但计算量明显增加，本次不采用，也不承诺抽帧绝不会漏掉瞬时露脸。

用户同时确认：同名照片和视频关联同一业务人员，不同组业务人员不同；但关联视频中不一定出现对应目标。文件名不是出现标签。

本设计修订 `2026-09-28-video-presence-design.md` 中以下规则：

- presence 不再继承合同视频的质量拒绝策略；质量告警与特征有效性分离。
- 增加有明确预算的邻近帧补采及候选级失败隔离。
- 解除 DTO、运行时和测试台“所有结果只能 INCONCLUSIVE”的限制，支持明确配置的试用阈值判定。
- 保留无阈值下的证据计算能力；不能把试用阈值描述为已经完成生产精度验证。

只修改独立 presence 能力及其 API 契约、测试台展示、测试和联调文档。保持旧 quick/full、图片核验、白底照和背景虚化语义不变。继续复用原 1024 维模型，不训练或下载新模型，不实现活体/反翻拍，不修改业务合同状态或自动审批。

## 2. 分层与处理链路

处理链路：参考照目标选择与特征提取 → 顺序解码和采样窗口 → 基础帧人脸候选分析 → 按需补采 → 所有有效候选逐一匹配 → 证据汇总 → 独立判定策略 → DTO/API/测试台。

模块职责：

| 单元 | 职责与边界 |
|---|---|
| `presence/config.py` | 冻结的 presence 专用质量提示、补采预算和判定配置，不修改共享合同质量配置 |
| `presence/quality.py` | 计算软质量提示、关键点/对齐技术有效性；不决定身份匹配 |
| `presence/analyzer.py` | 参考目标选择；逐候选对齐、1024 维特征提取；产出候选级观测和跳过原因 |
| `video/presence_decoder.py` 与 `presence/sampling.py` | 顺序解码、受控候选窗口、基础帧/补采选择、时间及覆盖统计 |
| `presence/decision.py` | 仅接收数值观测、完成状态和可信服务端配置，决定三类结果；不加载模型 |
| `presence/runtime.py` | 组合上述模块、截止时间和资源回收；不夹杂前端展示或业务审批 |
| `presence/contracts.py` | 严格校验结果一致性，禁止特征向量、模型内部对象和路径泄露 |

模型仍由独立且不可变的 presence runtime 持有。公共模块不得 monkeypatch 旧管线或复用可变旧视频策略。

## 3. 质量软提示与技术有效性

### 3.1 能提特征就比较

参考照和视频候选的亮度、清晰度、姿态、可见脸尺寸、边缘接近程度只形成质量提示，不能单独导致不提取特征。当前参考 112px、视频 64px 和关键点距图像边缘 2% 是经验策略，不是识别器的数学输入协议；它们可保留作提示界限，不能保留为 presence 的质量拒绝门槛。

低质量观测必须保留在匹配候选集合中，不能在“关键帧优选”时先过滤掉，也不能仅因质量低而在判定阶段将全部结果改回无法判断。质量用于触发额外取证、向调用方解释风险和同分时选取更清楚的展示证据。

参考照仍要求明确的目标：沿用主脸选择意图，小背景脸不直接拒绝；两个无法消歧的主体仍返回参考目标不明确，不擅自选择身份。主脸选择中的亮度、尺寸等软指标不得绕过本节要求成为隐藏的拒绝条件。

视频对每个受限候选独立处理，不要求全片只有一个人、同一人覆盖足够比例，也不只比较最大脸。

### 3.2 保留必要的技术校验

- 输入可解码，尺寸、像素和资源限制合法；可见裁剪区域非空。
- 五点坐标有限且能形成可用的对齐变换；拒绝非有限值、退化变换和无法定位的关键点。
- 对边缘候选使用明确的可见区域和对齐填充规则，不把“贴边”直接等同于“不可比较”。对齐后的有效图像来源区域必须非空；完全由填充产生的输出不可提特征。
- 眼距/嘴宽比例、严格眼睛水平度等经验阈值不再作为一票否决。必要的几何有效性检查应由退化点、越界点和极端变换测试证明，而不是复用整个旧质量配置。
- 对齐和识别器输入遵守现有协议；特征必须是有限、非零、可归一化的 float32 1024 维数组，版本为 `recognizer_v1_1024`。
- 不做生成式人脸修复，不将补出来的人脸细节作为身份依据；普通裁剪、旋转、对齐、缩放按原模型协议执行。

不承诺极端劣质输入必能识别。只有质量差但特征有效的候选应继续匹配；无有效特征必须真实记录，不能伪造分数。

### 3.3 局部失败隔离

无脸、候选关键点无效、不可对齐、特定候选的非有限/零特征属于可记录的局部不可比较；跳过此候选，保留同帧已得到的其他特征并继续后续帧。

模型会话异常、特征维度/版本错误、协议破坏、进程通信故障、解码失败和总超时是全局故障，不能吞掉或伪装为普通低质量。必须使用明确异常分类；未知异常默认全局故障，不通过宽泛 `except` 把所有错误降格为局部问题。

## 4. 有预算的基础采样与邻域补采

默认基础时间间隔 0.5 秒，每个窗口最多再分析 2 个邻近候选帧；这两个数值是工程采样配置，不是身份阈值。保留首帧和实际解码末帧，重复帧按真实帧号去重。

顺序解码按时间窗口生成基础帧及之后、下一基础帧之前的最多两个等距邻近候选，不对容器声明的末帧随机 seek。时间目标映射到最接近且不早于该目标的真实解码帧；低帧率下重复目标只保留一个真实帧。

分析每个窗口基础帧后，出现以下任一情况时分析该窗口剩余候选：无可比人脸、存在软质量提示、存在局部候选失败。候选处理上限被触及时也触发补采，以增加获取目标的机会；它不是取消预算限制的理由。补采候选中每张有效人脸均参与匹配，不仅保留最清楚或最大的人脸。

解码进程与父进程间使用有界窗口/流式协议，只保留当前窗口及交接所需少量帧，不把整段视频或全部窗口图像装入内存。必须保留可杀死子进程、管道超时、最大单帧像素和消费者退出回收机制。待传输窗口不允许形成无界队列。

总分析帧上限继续受 `resources.max_full_video_frames` 限制，默认 1200，包含首尾和补采。长视频不能因开头补采用完全部预算而完全漏扫后半段：预先按照“每窗口最多 3 帧、另留实际末帧”的最坏情况规划窗口数，必要时增大有效基础间隔以覆盖全时域；低预算则降低实际每窗口补采数。规划优先保证首尾和分布于全时域的基础帧，剩余额度才给补采。

例如默认预算能容纳约 399 个完整的三帧窗口及独立末帧；600 秒视频需要比 0.5 秒更大的有效基础间隔。具体调度须用实际帧去重和浮点时间边界测试约束，不能静默宣称仍为 0.5 秒全覆盖。

容器时长和帧数仅用于预估，实际解码仍强制执行像素、帧数、时长、上传字节与墙钟上限。若实际流使计划无法完成，记录不完整状态；不自动扩容，也不返回否定身份结论。

统计必须区分：解码帧数、实际分析帧数、基础帧数、补采帧数、可比人脸帧数、尝试候选数、成功比对候选数、局部失败候选数，以及检测候选上限是否触发。解码结束不等于每帧都做过检测或比对。

## 5. 判定模式与三类结果

### 5.1 配置与阈值来源

presence 新增服务端 `configured` 模式，要求明确的有限阈值 `-1 < threshold < 1`、非空 `threshold_id`，以及匹配当前模型、特征、采样和质量策略的配置指纹。配置版本与指纹随结果返回，部署快照可追溯。HTTP 请求不得临时传入任意阈值；测试台也不能替后端重算判定。

`configured` 表示“按指定试用阈值运行”，不是已经过统计验证的身份保证，返回 `calibration_status=CONFIGURED_UNVALIDATED`。本次不引入新的签名校准证书系统，也不允许仅改一个配置开关就对外宣称 `ACTIVE` 或生产精度已验证。

旧 `uncalibrated` 配置继续可加载：照样提取、比较并返回证据，结果附 `THRESHOLD_NOT_CONFIGURED`。此时主显示为“比对已完成，尚未配置判定阈值”，不再显示“缺少有效的签名校准”或暗示活体失败。无阈值不是代码永久禁止 FOUND 的理由；配置试用阈值后必须能通过相同真实运行链路返回三类结果。

不编造一个默认身份阈值。不使用同名标签或模型自己的最高分自动挑选并证明阈值。先完成不依赖人工标签的特征比对、配置和 UI 开发；再用业务人工确认的调参样本在实际部署环境选出试用阈值，由独立人员样本评估。人工标签未到位时，代码工作可继续，但不能声称现场判定阈值和识别精度已经验收。

### 5.2 明确的状态规则

数值匹配继续使用 1024 维 L2 归一化特征的点积，分数范围为 [-1, 1]，不是概率或百分比置信度。满足阈值的条件为 `score >= threshold`。出现检索允许一个有效候选构成命中，不增加连续多帧、最短露脸时长或全片覆盖率要求。

按以下顺序判定：

| 条件 | decision / found | 用户含义 |
|---|---|---|
| 全局失败、扫描未完成或参考目标不明确 | INCONCLUSIVE / null | 无法完成有效判断，保留已取得的数值证据及明确原因 |
| 没有任何成功比对候选 | INCONCLUSIVE / null | 未获得可比人脸，不等于证明目标未出现 |
| 未配置试用阈值 | INCONCLUSIVE / null | 已完成数值比对，尚无判定阈值 |
| 完整成功扫描且至少一个有效候选达到配置阈值 | FOUND / true | 本次扫描检测到匹配，即使其他帧质量差也不撤销命中 |
| 完整成功扫描、有成功比对、全部低于阈值，且无候选上限截断或局部候选失败 | NOT_FOUND_IN_SCAN / false | 本次实际扫描并比较的候选中未匹配到 |
| 有比对但候选截断或局部失败使否定结论不充分 | INCONCLUSIVE / null | 有证据但无法给出完整的未匹配结论 |

普通无脸帧和质量提示不等同于扫描不完整或局部系统失败。有限采样的 `NOT_FOUND_IN_SCAN` 不代表数学证明“整段视频从未出现”；文档及 UI 必须明确限定为本次扫描。

`success` 仍表示算法处理状态，不表示命中。试用阈值模式的 `suggestion` 保留 REVIEW，不输出业务自动放行 PASS；测试台以 presence 的 `decision` 作为主标题，以业务建议和阈值验证状态作为次级说明，不能再让 REVIEW 遮盖实际 FOUND。

## 6. API、证据与测试台

继续使用 `POST /api/v2/verify/video/presence`，multipart 必填 `reference_image` 和 `video`，输入限制与安全临时文件生命周期沿用现有接口。旧 quick/full 和其它接口不改变。

保留已有字段，并扩展以下契约：

- `comparison_status`：`COMPARED`（至少一次有效匹配运算）、`NO_COMPARABLE_FACE`（未取得视频可比特征）、`INVALID_REFERENCE`（未能明确并提取参考目标）、`FAILED`（全局故障）；全局故障优先，已算出的证据可保留。
- `calibration_status` 接受 `UNCALIBRATED` / `CONFIGURED_UNVALIDATED`，新增可空 `threshold`、`threshold_id` 和 `policy_fingerprint`；配置模式严格要求一致，未配置模式不得出现伪造阈值。
- `sampling_strategy` 和 `requested_sampling_interval_seconds`；原 `sampling_interval_seconds` 表示本次实际使用的基础间隔。新增 `base_frames`、`supplemental_frames`，两者之和等于 `sampled_frames`，实际首尾按分析类型计数且去重。
- 新增 `compared_candidates`、`failed_candidates`。`candidate_count` 保持实际尝试候选数；`valid_face_frames` 表示至少一次成功比对的视频帧数。
- `quality_warnings` 与阻断/运行原因分开；每条证据含真实帧号、时间、该帧最佳候选序号、分数和该候选质量提示。每帧保留最佳候选，最多返回 5 个不同帧；按分数、质量、时间作稳定排序，最高分不可因质量差被隐藏。

新增或细化原因码需区分：阈值未配置、局部关键点/对齐/特征无效、采样计划未完成和候选截断；低质量告警不得伪装为模型异常。DTO 严格验证状态、计数、阈值比较、证据排序及最佳分数/时间的一致性。

不返回原始照片、视频、向量、关键点数组、服务器路径或堆栈。特征只在本次任务内存中使用；现有模型版本摘要继续返回。最多五条证据是展示上限，不是实际比对候选上限。

`liveness_evaluated=false` 作为已有兼容字段保留，文档说明“未执行且本接口不要求”，不展示为失败原因或影响三类结果。

测试台展示顺序：匹配/未匹配/无法比较 → 最佳分数及使用阈值 → 证据时间及质量提示 → 实际扫描统计 → 试用阈值与业务审核说明。已有本地视频预览可跳转到证据时间查看；不新增服务端截图存储或媒体下载接口，不因布局改动引入无关前端重做。

新测试台识别带新增字段的新契约；对旧响应保持历史含义，对未知或不一致的响应显示协议错误而非匹配成功。联调文档记录新增枚举和不再恒定 INCONCLUSIVE 的兼容影响，调用方不得继续把枚举当作常量。OpenAPI 与后端和 UI 同步更新。

## 7. 测试数据、标签和阈值验证

100 组现场素材使用匿名编号，仅有身份分组关联。所有照片-视频对的初始出现标签为 `unknown`。不同组照片可组成不同人图片对，但不能据此把不同组照片与视频无条件认定为负例，因为视频可能出现多个人。

人工标注表与算法输出表分离：匿名 reference_id、video_id、身份分组、`present/absent/uncertain`、出现时间段（present 时）、标注来源及版本。业务人员看完整视频作判断，默认不先展示模型分数，防止评分诱导；关键帧只用于辅助定位，不能仅靠抽帧判定 absent。无法肉眼确认时标 uncertain，不由模型补标签。

原媒体、原始文件名到匿名编号的映射、人员标签与逐例结果留在本地受控/忽略目录，不加入公司 Git。可提交不含身份信息的工具、空白标签格式、合成夹具和汇总报告；不得提交生物特征。

先按人员固定调参集与留出评估集；照片、对应视频及同一视频的所有帧不能跨集。如果多人视频跨越身份分组，两端关联人员应落在同一集合，否则排除该样本，避免泄漏。

在 37 服务器拟部署的相同镜像、模型和策略下，用人工标签调试试用阈值；保留整段视频最大候选分数的决策口径，不能用逐帧准确率替代视频级结果。阈值候选与各自误报/漏报/无法判断数量全部可追溯；没有业务可接受风险目标时只给出权衡结果，由业务选择试用点，不自称满足生产门槛。

留出集只用于最终评估，不用它再选阈值。报告标签数量、已知正/负样本数、uncertain 数、可比较比例、无法判断比例、视频级误报和漏报，以及暗光/模糊/侧脸/小脸/多人/短暂出现的分层表现和耗时。样本不足以支持精度结论时如实说明；不能把“96 组可评分”写成 96% 准确率。

试用结果可直接供开发联调，但不代表已经满足身份核验、活体或合同自动签署的生产要求。正式业务阈值验收需要人工标签和风险目标，不能由开发联调的 synthetic 测试替代。

## 8. 验收、兼容和后续发布边界

自动化必须覆盖：

- 暗、糊、侧脸、小于旧尺寸界限、关键点近边缘的有效人脸仍调用特征提取和匹配；确实不可对齐或全填充不会生成假特征。
- 一帧多个目标、目标非最大、一个候选失败、后续帧恢复，均保留已完成的比较；协议/维度错误仍整体失败。
- 基础帧差而邻近帧可用、低帧率重复帧、实际首尾、短暂出现、长视频预算均匀分配、实际时长偏差和子进程回收。
- 模拟明确的配置阈值，在真实组合层/API/测试台分别得到 FOUND、NOT_FOUND_IN_SCAN、INCONCLUSIVE；测试阈值只用于合成夹具，不是生产阈值。
- 无阈值时能返回数值比较，UI 不渲染缺签名或活体失败；FOUND 不被 REVIEW 标题覆盖；不把相似度当准确概率。
