# 01 技术路线与架构

## 1. 技术路线演进

| 阶段 | 做了什么 | 结果 |
|---|---|---|
| 原始版本 | 预编译闭源库 `libface_sdk_jni.so`（FaceBoxes → 5 点 → FSANet → 1024 维特征）；每帧 JPEG 回环、传感器方向直接送活体 | 慢；活体在实测中放过 2/3 的攻击、误拒 1/4 的真人 |
| 止血 | 去掉 JPEG 回环，转正方向后再送活体 | 同一批片段上，活体误拒和放过都降到 0 |
| A 阶段：自研重写 | C++ 重写同一套模型，与 Python 注册服务逐位对齐；int8 量化；跟踪 + 每人只提一次特征 | 速度大幅提升，特征与服务端兼容；LFW 准确率仍只有 88% |
| B 阶段：换模型 | 可切换的 InsightFace：SCRFD 检测 + ArcFace 对齐 + MobileFaceNet / IResNet-50 | LFW 在误识率十万分之一（FAR 1e-5）时的通过率从 88% 提到 99.6% |
| 对标虹软 | 照虹软 Demo 的组织方式：跟踪替代逐帧检测，活体与提特征并行，结果出来立即判定 | 从进画面到识别的时间与虹软同一量级 |
| 级联 | 先用 MobileFaceNet，只有拿不准的才交给 IResNet-50 int8 | 准确率接近单用 R50，多数人只花 MBF 的时间 |
| 本版：安全与可信 | 生命周期护栏、图库代际、有界收尾、结构化对标记录 | 迟到和过期的结果不会再放行；对比数据可以审计 |

## 2. 模块组成

```text
android-sdk/
├─ face-core     引擎 SDK（Java + C++）
│   ├─ engine/   FaceSession 会话状态机、跟踪、图库、各推理引擎的封装
│   ├─ cpp/      libfaceengine.so：ORT 推理、SCRFD、ArcFace 对齐、图像转换、JNI
│   └─ live/     静默活体（ncnn，MiniFASNet 两模型）
├─ app           业务 App：CameraX 采集、识别界面、同步
└─ face-bench    对标台架：录制片段、多后端回放、虹软对照（虹软 SDK 只在本地编入）
tools/engine-eval  评测脚本（LFW、量化、级联阈值、会话审计报告）
tools/face-eval    对标总报告
FaceFeatureExtractorAPI  Python 注册服务（服务端 v1 特征）
backend-java       平台后端（人员、分组、同步、1:N 搜索）
```

## 3. 每帧处理流程

```text
CameraX YUV_420_888（KEEP_ONLY_LATEST，单分析线程）
  │ [候选] 空闲帧在读取像素平面之前就跳过
  ▼
原生打包 NV21（一行一次 memcpy）
  ▼
FaceSession.onFrame ── 分析线程
  ├─ 检测：RoiTracker
  │     · 每 10 个分析帧做一次全图检测（SCRFD，长边 320）
  │     · 其余帧只在每张已知人脸周围 2 倍区域内检测（采样到 160）
  │     · 区域里没找到人，下一帧立即回到全图检测
  │     · 只转换检测需要的像素：先缩小 Y/UV 平面，再转颜色
  ├─ 关联：FaceTracker（IoU 关联、框平滑）
  ├─ 过滤（全部 O(1)）：人脸 ≥64 像素、不越界、连续 5 帧稳定、
  │     五点估计姿态 yaw ≤30° pitch ≤25°、亮度 40–235、相对清晰度 ≥0.6
  └─ 对通过过滤、尚未判定的人，同时提交两个任务：
        ├─ 活体 worker：复制整帧 → MiniFASNet ×2（2.7 倍与 4.0 倍上下文，80×80）
        │     阈值 0.7；先到的 2 票都是真人即通过，不必等满 3 票
        └─ 特征 worker：1.6 倍人脸裁剪（full-range BT.601）
              → 用跟踪得到的五点做 ArcFace 112 对齐（不重复检测）
              → MobileFaceNet 512 维 → 图库余弦搜索（取前两名）
              → 级联：≥0.487 直接通过；<0.098 直接拒绝；
                       介于两者之间 → IResNet-50 int8，≥0.31 才通过
  ▼
两个任务里后完成的那一个，在自己的线程上立即判定
  ▼
统一成功门禁：
  任务代际仍有效、仍在等待判定、活体为 ALIVE、人脸仍可见且仍通过过滤、
  两级图库属于同一个已就绪的发布代
  ▼
识别事件（同一身份 5 秒内不重复报）
```

## 4. 线程与资源

| 线程 | 工作 | 推理线程数 |
|---|---|---|
| CameraX 分析线程 | 打包、检测、跟踪、过滤、提交任务 | SCRFD：ORT 2 线程 |
| 活体 worker | 活体推理 | ncnn 2 线程 |
| 特征 worker | MBF / R50 推理、图库搜索 | 每个识别模型 ORT 4 线程 |

- ORT 线程空转（spinning）关闭，避免各条线程互相抢大核。
- 同一时间每条 worker 只有一个任务在跑，新任务不会叠加排队。
- `NativeEngine` 和 `NativeLiveness` 的推理与释放共用同一把锁。退出时先让会话停止授权，再等任务排空，最后才释放原生句柄；等不到就保留句柄，不在推理进行中释放。

## 5. 会话安全设计（本版新增）

- 每个异步任务都带上会话代、轨迹号、尝试号、帧号和图库代。任务开始、完成、进入级联、最终成功时都要重新核对，任何一项对不上，结果就作废。
- `reset()`（例如切换摄像头）会开启新的观察代，但仍在运行的原生任务会继续占着自己的引擎槽，直到真正结束。
- `finish(timeoutMs)`：停止接收新帧，等待已接收的帧、已提交的任务、级联后续任务和回调全部完成，等待期间不持会话锁。超时就永久撤销该会话的授权。
- 图库发布：开始改数据前先让旧的发布代失效；所有特征空间（MBF 和 R50）都刷新成功后，才标记为就绪。删除人员、刷新失败、发布空库，都会撤销已经匹配上的旧结果。
- 回调在锁外从队列里依次发出。将来如果接入开门等实际执行动作，必须在执行那一刻重新核对事件携带的图库代，不能把"收到回调"当作完整的授权链。

## 6. 关键参数（本版默认值）

| 参数 | 值 | 来源 |
|---|---|---|
| 全图检测长边 / 区域检测长边 | 320 / 160 | DOOGEE 实测 |
| 全图检测间隔 | 每 10 个分析帧 | 实测；还没有按时间设上限，见改进路线 |
| 空闲时分析间隔 | 100 ms | |
| 稳定帧数 / 允许移动比例 | 5 / 0.08 | 参照虹软 Demo 的组织方式 |
| 姿态上限 | yaw 30°，pitch 25° | 与注册服务一致 |
| 活体 | 阈值 0.7，3 票里 2 票 | 需要用现场数据重新校准 |
| MBF 阈值（单模型时） | 通过 0.33 / 下限 0.28 | LFW，FAR 1e-5 |
| R50 int8 阈值 | 0.31 / 0.26 | LFW，FAR 1e-5 |
| 级联 | 通过 ≥0.487，拒绝 <0.098，中间交给 R50 ≥0.31 | `tools/engine-eval/cascade_lfw.py` |
| 失败退避 | 1 s 起，每次翻倍，最多 8 s | |

## 7. 数据与同步

- 服务端仍按 v1（1024 维）提取并保存注册特征，同步协议 v2 不变。
- 选用 InsightFace 引擎时，设备根据同步下来的注册照**在本机提取特征**，并按照片文件缓存（`*.f32`）。服务端 1:N 搜索仍走 v1。若服务端也要改用新特征，需要增加按特征版本区分的存储和迁移，不在本版范围内。
