# 管理后台大数据量修复设计

日期：2026-09-22
状态：已通过独立规格评审，用户已批准实施；实际完成情况以实施计划和验证报告为准。
依据：[审查报告](../../reports/2026-09-22-backend-management-review.md)。
已确认约束：现场 Android 设备能否升级暂不确定，必须按兼容旧设备设计。此次不新增导出业务，不改人脸模型、特征维度和识别阈值。

## 1. 目标与方案选择

直接目标：管理页面只查询、传输和渲染当前页，不能随十万人员规模增长为十万行对象；正常浏览、筛选、编辑和批量删除有明确的资源边界和正确的结果反馈。

整体目标：同步、搜索、算法请求和通知各有资源边界；设备最终与后台数据一致；管理身份和设备身份分离；故障不会无限占用公共请求线程。

| 路线 | 范围与代价 | 判断 |
|---|---|---|
| 只修管理列表 | 分页、窄字段和前端刷新，改动最小；同步与算法等待仍可能影响后台 | 作为第一个交付阶段 |
| 在现有工程分阶段治理 | 保留 Spring Boot/MyBatis-Plus/Vue/Element Plus，拆开查询用途，逐步补资源限制和新同步协议 | 推荐总体路线 |
| 重建后台并引入向量数据库/消息中间件 | 可支持更复杂检索与多节点场景，但增加迁移、维护和部署成本 | 当前不采用，后续由实测需求决定 |

不重写前端，不立即引入 Redis、Kafka 或独立向量数据库。生产配置与协议升级分阶段发布，每阶段保留可验证的退出条件。

## 2. 分阶段交付

| 阶段 | 交付结果 | 能解决的问题 | 仍需明确的边界 |
|---|---|---|---|
| A：管理查询与页面 | 人员/分组分页、远程分组选项、窄 DTO、单次刷新、批量结果、关闭逐行日志 | 当前最直接的页面卡顿与重复请求 | 不代表设备同步、算法等待和安全问题已全部解决 |
| B：服务可用性与管理安全 | 算法超时/有界并发、搜索分块和限时、异步有界通知、登录鉴权、文件清理及配置治理 | 避免慢依赖占满线程，阻止匿名管理操作 | 旧设备仍使用旧全量协议，只能有限兼容 |
| C：同步协议和 SDK | 版本化分块/增量、墓碑、持久化游标、重连追赶、影子数据集切换 | 大库同步与删除一致性 | 设备升级安排决定何时退出旧协议 |
| D：预发验证与上线 | 独立 MySQL 验证、十万合成数据、多设备/慢依赖压测、灰度与回滚记录 | 证明目标负载下的实际行为 | 未通过不得宣称十万级生产容量已验证 |

A 是本轮首先实施、可以独立评审的工作包。B、C 分别形成详细设计后逐段实现；下文明确其架构约束和任务边界，避免一次提交混入所有子系统。

## 3. 第一阶段详细设计

### 3.1 分离三种查询用途

- `AdminUserQueryService`：管理表格、详情展示与计数。列表只读窄字段，不返回特征。
- `FaceSearchService`：特征匹配。后续使用 ID 游标读取必要特征字段，不能复用管理分页的当前页。
- `SyncService`：设备协议。旧客户端把数组当完整名单，不能将管理分页结果直接复用。

第一阶段不把现有 `getUsers()` 简单改成只返回第一页；先增加独立管理查询通道。待 B 实施搜索分块后再移除其无界内部调用。禁止在 `User.featureData` 上全局加 JsonIgnore，因为同步仍需要该字段。

### 3.2 管理接口契约

新增分页接口，同时保留有界的旧接口过渡。管理页面全部切换到新接口。

| 接口 | 参数 | data 内容 |
|---|---|---|
| `GET /api/users/page` | `page=1,size=20,name?,groupId?` | `records,total,page,size` |
| `GET /api/groups/page` | `page=1,size=20,keyword?` | `records,total,page,size` |
| `GET /api/groups/options` | `keyword?,afterId?,limit=20` | `items,nextCursor,hasMore`；每项仅 id/groupName/groupNo |
| `GET /api/groups/{id}` | 已选分组 ID | 沿用详情结构，供编辑框回填当前分组 |
| `GET /api/users/count` | 无 | 继续返回全局有效人员数量，只在需要全局统计时查询 |
| `GET /api/groups/count` | 无 | 返回分组总量，替代前端 groups.length |

统一分页示例：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "records": [{
      "id": 123,
      "userNo": "example-user-number",
      "name": "示例人员",
      "groupId": 7,
      "groupName": "示例分组",
      "photoUrl": "example.jpg",
      "hasFeature": true,
      "status": 1,
      "createTime": "2026-09-22T09:00:00",
      "updateTime": "2026-09-22T09:00:00"
    }],
    "total": 100000,
    "page": 1,
    "size": 20
  }
}
```

约束：页大小 1–100；page 为正整数，使用 long 校验 offset 溢出，第一阶段 offset 上限 1,000,000，超过返回 400 并提示缩小范围；参数不合法不得退化为全量查询。options 的 limit 为 1–50，按 id 升序取 limit+1 判定 hasMore。默认值是初始保护配置，不表示已验证的服务器容量。

分组 page 的 keyword 与 options 的 keyword 均为最多 100 字的名称包含匹配，按文字转义 LIKE 通配符；afterId 必须是非负整数。第一阶段不为下拉引入新的全文索引或改变分组字段名称。

姓名保留“包含匹配”的使用语义，参数长度上限 100，参数化 SQL 并将输入中的 LIKE 通配符按字面含义转义。人员按 `create_time DESC,id DESC` 稳定排序；分组按 `id DESC` 排序。分页使用数据库 LIMIT/OFFSET，禁止读出全集后 subList。

SQL 投影直接映射 `UserListItem`，字段包括 groupName 和 hasFeature，不取回 feature_data；groupName 用一条 LEFT JOIN 或当前页有限批量查询补齐，不能逐行 N+1，也不能加载所有分组做映射。hasFeature 在 SQL 中按现有“特征字符串长度大于 20”规则生成，以保持已有数据展示语义；B 再对新写入做真正的维度/有限数值校验。

### 3.3 旧管理列表兼容

`/api/users/list`、`/api/groups/list` 不保留无上限读取，也不静默截断成“前 100 条就是全部”。

- 使用 SQL LIMIT 101 预读；匹配结果不超过 100 时维持旧 data 数组和兼容字段。
- 超过 100 时 HTTP 409，`errorCode=PAGINATION_REQUIRED`，提示迁移至 /page；不返回部分名单。
- A 修改管理页面后不再调用旧列表；B 对新旧管理接口统一鉴权。旧列表进入弃用文档和访问计数，随后按实际调用清单下线。
- 此规则只用于管理列表，**绝不能套到设备 `/api/sync/users` 上返回部分 data**。

### 3.4 前端页面

保留当前 HTML/Vue/Element Plus 结构，增加必要的分页与加载状态，不进行视觉重做。

1. 人员/分组分别维护 page、size、total、loading、error 和当前页 records；表格页大小 20/50/100。
2. 切换筛选重置到第 1 页。每条列表请求使用 AbortController 和请求序号，旧请求不能覆盖最新筛选、不能错误关闭新请求的 loading。
3. 分组管理列表、人员筛选选项、人员编辑选项拆分状态。选项远程搜索加 300 ms 防抖，有界加载；已选分组按 ID 单独回填，不能因不在当前选项页而丢失显示。
4. 人员行直接使用 groupName，不依赖完整 groupMap；统计显示真实 total，不再显示 groups.length。
5. 新增/编辑成功只执行一次当前人员页刷新。修改姓名/照片不刷新分组列表；全局统计在概览进入或确有数量变化时刷新，避免重复 count。
6. 删除当前页最后一条后必要时回退一页再加载。切页/筛选清空选择；“全选”明确为本页，不能默认跨十万人选择。
7. 当前页头像按需加载，设置宽高与 `loading=lazy`；释放本地预览 Object URL。第一阶段不批量改写已有照片或生成全库缩略图。
8. 一次操作只展示一次最终成功/部分失败/失败信息；处理 400、409、429、503 等明确错误，不无限自动重试。

### 3.5 批量删除与通知

批量删除采用有界的“逐项结果”语义，单次最多 100 个 ID，校验非空、正整数并去重，处理前拒绝超限请求。

`data` 返回 `requestedCount,successCount,failureCount,successfulIds,failures[{id,errorCode,message}]`。某项失败必须出现在 failures，不再使用无条件“批量删除成功”。全部成功使用 HTTP 200/code=200；部分成功使用 HTTP 207/code=207；全部逐项失败使用 HTTP 422/code=422，仍返回 failures。前端明确处理这些结果，旧页面不得因 code=200 把部分失败误报为全成功。鉴权/参数/整体不可执行错误使用对应 HTTP 状态，不进入部分执行。

提取不广播的单项删除内部方法，批次完成后只发一次通知；单条删除仍发一次。数据库删除结果作为成功标准，照片清理失败记录为可重试回收，不能把已完成删除报成未删除。网络通知失败不能覆盖数据库处理结果。详细异步队列与每会话隔离在 B 完成。

删除预读仅取 id/photoUrl 等元信息，不读取完整特征。单项独立提交，避免整个批次事务里吞异常导致全部回滚却返回部分成功；连接不可用等系统性失败立即终止后续尝试，未执行项明确标记为 NOT_ATTEMPTED，不串行累积 100 次连接超时。重复 ID 按目标只执行一次，同时返回 uniqueCount；已不存在按幂等目标达成记录在 alreadyAbsentIds 中，不能计为本次实际删除。只有实际删除过人员才广播。

计数关系固定为：requestedCount 是输入原始数量；uniqueCount 是去重数量；successfulIds 包含实际删除和已不存在的 ID；successCount 等于 successfulIds 数量；failureCount 等于 failures 数量，包含 NOT_ATTEMPTED；successCount+failureCount=uniqueCount。另返回 deletedCount 表示本次实际删除数，alreadyAbsentIds 单独列出。全部已不存在属于幂等成功，HTTP200、deletedCount=0、不广播。

### 3.6 数据库与配置

- 新装 schema 增加与用户列表匹配的候选索引：`(status,create_time,id)`、`(group_id,status,create_time,id)`。执行计划决定保留组合，不机械增加全部索引。
- 为存量库提供显式、可复核迁移 SQL，检查已有索引后执行；不依赖 `CREATE TABLE IF NOT EXISTS` 自动修旧表，不自动连接当前配置中的数据库。
- 姓名 `%包含%` 不会靠普通 name 索引变成常量时间；保留行为并监控实际扫描量。第一阶段不改变搜索语义，也不承诺深页性能等同于首页。
- MyBatis 换用 SLF4J，关闭结果 TRACE；日志不输出特征、图片和口令。为 SQL 设置有限 statement timeout 并验证驱动行为；初始值 5 秒，在预发调整。
- 增加测试 profile，数据库配置与现有环境彻底隔离，测试不读取生产连接信息。

## 4. 第二阶段架构约束

### 4.1 算法和搜索

- Java 显式设置连接/读取时限；初始连接 2 秒、读取 10 秒、总预算 15 秒，算法并发默认 2、无无限等待队列。过载快速返回 429/503，不占住额外工作线程排队。总预算到期须取消实际 HTTP 交换并关闭连接，不能仅靠 Future.get 返回超时而让后台网络请求继续占槽；以持续分片响应故障注入验证这一点。
- Python 路由将解码/推理交给有界执行器；初始单推理槽保护全局模型。槽位要保持至底层任务真正结束，客户端取消不等于推理已停止，不可提前释放造成超并发。健康检查不经过推理队列。长期不恢复时就绪检查降级、报警并由部署监督机制重启算法进程；线程方案不宣称能杀死原生推理。若要求不重启服务而恢复单个永久挂起任务，必须另用受监督工作进程，不能伪装成普通超时配置已解决。
- FaceSearchService 先采用 ID 游标分块扫描必要字段，默认每批 200、并发 1，并设置总时间预算；每块维护全局最佳匹配。超时返回“未完成”，不能当作“未找到人员”。此方案解决峰值内存与资源争抢，不改变 O(N×D) 复杂度。
- 是否引入紧凑向量缓存/ANN，依据预发搜索延迟和模型准确率再决定；新增向量索引不得改变现有阈值而不做识别质量验证。

### 4.2 WebSocket

业务写入完成只提交一次合并后的“需要同步”信号；每会话使用串行、有界发送，慢会话不会阻塞其他会话或 HTTP 写线程。可用 `ConcurrentWebSocketSessionDecorator` 配合有界分发器，但需同时验证单次底层阻塞发送的容器时限，不能只依赖装饰器事后检查。队列合并可丢重复提示，不可丢持久化变更；设备通过版本查询补齐。

### 4.3 身份与配置

- 管理端改用 Spring Security 会话认证，HttpOnly/SameSite Cookie、CSRF、登录退出与过期；管理员密码从环境注入的密码哈希加载，没有配置时禁止以默认演示口令启动生产配置。前端 fetch 与登录页同时改。
- 新设备使用独立、可撤销、带权限范围的设备凭据，不共用管理员 cookie。
- 旧 SDK 不会发送凭据，不能用“新版加鉴权、旧路径永远 permitAll”解决。确需继续支持时，只能在已核实的专用设备网络/网关暴露最小旧路由，管理路由不在该通道开放；设置明确到期配置和迁移清单，默认关闭兼容模式。
- 旧通道的网络范围、绝对到期日期、实际设备清单是上线输入，而不是本地编码前置条件；未配置这些输入，生产不得开启旧匿名兼容通道。这是受限网络过渡，不等同于已实现强设备身份。
- 数据库使用最小权限账号，不再发布公网/全部接口端口；新安装要求环境密钥。存量密码轮换和网络切换编写操作步骤，不自动修改运行中的数据库账号。

### 4.4 文件与一致性

上传进入暂存目录，验证和数据库成功引用后转为正式文件；失败删除新临时文件。换照在新引用成功后安排旧文件回收，失败可重试。孤儿巡检先 dry-run 清单、设置宽限期，不直接批量删除存量照片。

人员并发重名规则需明确未分组/禁用记录语义后建数据库约束；先查重、形成迁移报告，不自动删除或合并同名人员。设备注册使用原子 upsert。错误响应与日志只包含必要信息。

## 5. 第三阶段：兼容迁移的同步协议

### 5.1 旧协议边界

v1 保留完整名单契约，不分页、不静默截断；限制生成与下载并发，合并广播。确需承载旧设备的大库，可在事务一致快照中流式生成磁盘快照，完成后原子发布，供多设备复用；生成未完成/失败不能替换最近完整快照，首次没有完整快照时返回错误而非空名单。

服务器流式传输只能控制服务端堆，不能解决旧 SDK 全量 JSON 和本地数据库处理的上限。不能承诺不升级设备也能支持任意规模。历史快照有最大陈旧时间并标记；不能无限返回旧数据掩盖同步失败。旧协议是否继续启用、允许的数据量和并发，以目标设备预发测试和迁移窗口决定。

### 5.2 v2 发布版本与删除记录

新增数据库 `sync_revision` 单行版本计数与 `user_change_log`，人员行保存 syncVersion；时钟同时维护 epoch 和 retentionFloor。所有人员增改删和其他会改变同步内容的写入，在一个短事务中锁定版本行、分配版本、写业务表和变更日志，一起提交；锁保持至提交，回滚不推进可见版本。统一锁顺序，文件传输和算法提取必须在此事务之前完成。不能使用普通 AUTO_INCREMENT ID 或响应时间替代安全提交水位。分组删除与人员创建/换组也走统一锁序并在事务中校验，避免外键 ON DELETE SET NULL 绕过日志。

日志事件包含 upsert/delete、人员 ID、版本、变更后同步所需字段/特征，删除保留墓碑。消费者分页只读取目标版本 U 以内的已提交事件，按版本推进；事件重放须幂等。独立写数据库的其他程序必须接入同一发布约束，否则本方案不能保证无漏变更。

如设备配置了按组授权，事件还必须保留变更前/后的组归属：从允许组移出的人员向旧范围生成删除效果，移入新范围才提供 upsert，不能仅用当前组过滤日志。设备授权范围改变时使其同步授权版本失效并要求重新初始化，防止范围缩小后本地残留人员。

### 5.3 初始数据与追赶

1. 开始时在一个短一致读事务中取得已提交起点 L 和已提交人员最大 ID M，并建立同步租约，保证所需日志不会在过程中清理。
2. 用 ID 游标读取 `id<=M` 的人员至客户端 staging 数据集，使持续新增时初始扫描仍有终点；禁止对当前在线库按每页执行缺失删除。
3. 扫描结束取得上界 U，重放 `(L,U]` 变更，覆盖扫描期间的新增/修改并应用删除墓碑；以每人已应用版本避免旧事件覆盖页面中读到的较新状态，墓碑同样保留版本。
4. 所有页和变更成功后，设备在本地事务中切换完整数据集并记录 U；失败或断电保留原在线库，允许恢复或重建。
5. 后续从已确认游标读取增量；通知仅提示去追赶，重连、定期检查和同步期间 pending 标记都能触发补拉。

分页扫描需防止“较小 ID 先分配、较晚提交”越过扫描游标；变更日志完整 postimage 和 `(L,U]` 追赶负责补齐，U 前所有提交必须受同一版本锁约束。staging 的中间状态绝不用于实时识别。最终切换后还需使识别内存缓存/索引切换到同一版本，不能只更新 SQLite。

墓碑/事件按已确认游标及保留策略回收；超过保留窗口的设备收到显式 `SNAPSHOT_REQUIRED`，执行完整重建，不能继续返回不完整增量。照片按版本下载，修正相对 URL，并设置读取时限。

游标与 epoch/授权版本绑定；备份还原、绕过日志修改数据或回退到旧写路径时必须切换 epoch。历史查询与 retentionFloor 校验使用一致性读，确保清理并发时返回完整页或明确重建，不能成功跨过已清理区间。

### 5.4 发布顺序

先部署同时支持 v1/v2 的后端与增量日志，再升级测试设备，再灰度真实设备；记录协议、游标、失败和滞后。新旧设备并存期保留 v1 完整语义，达到截止日期后关闭旧通道。回滚新版 SDK前必须确认旧版本本地库兼容；不能直接降版本打开新 schema 后执行破坏性重建。

## 6. 验收与可用环境

当前已找到 JDK 21/Maven（目标 Java 17）、Node、浏览器；Java 工具使用已验证的绝对路径。当前未发现可直接运行的 Docker/Podman/MySQL，因此先执行单元/MVC/页面回归，再配置独立 MySQL 8 测试实例或可用 CI。H2/Mock 测试不能代替 MySQL SQL、索引和事务验证。

Python 本机运行时与 Docker Python 3.10 不等价，且缺少实际模型运行依赖。算法路由可通过注入推理替身验证并发、取消、超时和健康检查；实际模型测试须使用隔离且依赖齐全的目标运行环境，不改变现有环境包来掩盖问题。

### 第一阶段硬性验收

- 0/1/20/21/100/101/100000 条数据的分页边界正确；相同创建时间稳定排序；总数、分组名、筛选和空页正确。
- 新人员 page 响应没有 featureData；数据库最终列表 SQL 含 LIMIT，不能先全量取回再 DTO 转换。
- 非法 size/page 被拒绝；旧列表 >100 明确失败，<=100 完整返回；旧设备同步契约未被修改。
- 页面只渲染当前页；编辑一次只触发一次列表刷新；筛选快速切换时过期响应不能覆盖最新结果。
- 分组超过 100 时仍能远程搜索和编辑回填；分组总数显示真实值。
- 批量部分失败逐项可见，超限不执行，成功批次只广播一次；关闭逐行 SQL 结果日志。
- 特征检索没有因管理分页漏掉后续页匹配；设备同步没有因为管理查询改动而清空本地人员。

### 上线性能与可靠性验收

固定并记录测试硬件、JVM 堆、MySQL/算法配置，使用十万条合成人员与 1024 维特征。初始目标：20 个管理并发下首页及常规筛选 p95 不超过 1 秒，非人为故障请求错误率低于 0.1%；该目标须实测，不作为当前承诺。深页单独统计，不用首页结果代替。

记录接口耗时、响应字节、堆/GC、请求线程、数据库扫描/慢 SQL、队列长度与拒绝数、同步滞后、日志和磁盘。慢算法、慢 WS、批量失败、断线重连、同步中删除、进程退出等故障必须有可重复测试。内存应受页/批次/并发限制，而不是随人员总数线性保留完整列表。

认证与迁移验收必须同时覆盖：匿名管理拒绝、合法管理 CSRF/session、过期会话、设备权限、关闭/过期的旧通道、禁止从旧设备入口访问管理路由。

## 7. 发布、回滚与完成定义

- 本地实现和测试使用工作目录中现有未提交代码作为基线，不从仅有算法基线的 HEAD 创建一个缺失后端的 worktree。记录文件哈希，只提交本次明确变更。
- 数据库迁移先在独立库验证，预发备份/核对索引和查重后执行；新版本先添加结构再启用功能，不自动删除旧结构。
- 后端先支持新管理接口，随后同一发布更新 HTML；旧列表保护以回归测试覆盖，避免前端更新顺序引入无提示截断。完整发布包必须包含匹配的页面和 API。
- 灰度出现异常时回滚匹配的应用/页面版本；索引通常保留即可。回滚到存在无界查询的旧版本不代表恢复安全，应同时限制入口和负载。
- “阶段完成”需要代码、回归测试、迁移说明、API 文档与验收记录；“全部修复完成”还需要 B/C/D 的边界和现场设备迁移全部验收，不能以 A 完成代替全系统完成。

确认本设计后，先执行 A；B/C 的详细工作包在各自开始前补充其可执行测试和迁移步骤，不要求一次批准任何生产数据写入或正式发布。
